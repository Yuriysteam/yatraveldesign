# Формат отчёта

Вывод состоит из вводных, результата проверки экспериментов, краткой сводки вопросов и таблиц платформ. Короткая фраза допустима только для блокера. Не предлагай публикацию отчёта в Figma.

## Вводные

| Поле | Значение |
|---|---|
| Тикет | Прямая ссылка или ключ |
| Figma | Ссылка на проверенную борду |
| Часть продукта | Проверенная область Travel |
| Платформы | Web / iOS / Android |
| Код | Режим проверки: индекс Arcadia или checkout; фильтр путей; ревизия индекса либо путь, ветка, ревизия и дата проверки checkout |
| Граница пути | Точка входа → первое устойчивое состояние после эффекта фичи |
| Проверенные источники | Тикет, Figma, пути к коду |
| Не удалось проверить | Недоступные или неоднозначные источники; `Нет`, если ограничений нет |

## Эксперименты

Размещай результат проверки экспериментов сразу после `Вводных`. Показывай только флаги и ветки, найденные в проверенном коде. Наличие ветки подтверждает вариант поведения, но не её фактическую включённость в продакшене.

| Эксперимент или ветка | Платформа | Условие | Что меняется | Подтверждённость | Источник |
|---|---|---|---|---|---|
| … | Web / iOS / Android | Флаг, вариант или условие ветвления | Видимое состояние, действие или переход | Найдено в коде; включённость не проверена | `path:line` |

Если эксперименты не найдены, не создавай таблицу. Напиши: `Эксперименты не найдены в проверенном коде`, затем укажи проверенные платформы и границу поиска. Не обращайся к отдельной системе конфигурации экспериментов без прямого запроса пользователя.

## Краткая сводка вопросов

Размещай сводку после результата проверки экспериментов и до таблиц платформ. Включай все уникальные вопросы из столбца `Вопросы` платформенных таблиц. В таблице сохраняй полную формулировку вопроса, а здесь кратко передавай его смысл без потери существенного условия. Указывай платформу и связанные ID состояний.

- `Web · W-01` — Краткая формулировка вопроса.
- `iOS, Android · I-03, A-08` — Краткая формулировка общего вопроса.

Не назначай вопросам отдельные ID. Одинаковые по смыслу вопросы объединяй в один пункт и перечисляй все связанные платформы и ID состояний. Если открытых вопросов нет, напиши `Открытых вопросов нет`.

## Таблица платформы

Создай отдельную таблицу для каждой выбранной платформы. Расположи шаги в порядке пользовательского пути. Все состояния одного шага должны идти непосредственно друг под другом; внутри шага сначала ставь состояния со статусами `🚫` и `⚠️`, затем состояния со статусом `✅`.

| ID | Шаг пути | Состояние | Условия | Поведение или ограничение | В спеке | Вопросы | Источник |
|---|---|---|---|---|---|---|---|
| W-01 | … | … | … | Код: … / Ограничение API: … / Конфликт: код делает X; тикет требует Y; в Figma показано Z | ✅ Точное состояние показано — [Figma](https://www.figma.com/design/FILE/NAME?node-id=1-2) / ⚠️ Показана только часть — [Figma](https://www.figma.com/design/FILE/NAME?node-id=1-2) / 🚫 Состояние отсутствует | Конкретный открытый вопрос / — | `path:line`, ссылка на тикет или точный узел Figma |

Правила заполнения:

- `ID`: `W-`, `I-` или `A-` для Web, iOS и Android. При повторном запуске сохраняй ID строки, если совпали платформа, шаг пути, состояние и условия; новый ID выдавай только новому состоянию.
- `Состояние`: одно наблюдаемое состояние, без объединения через «и» нескольких случаев.
- `Шаг пути`: повторяй значение в каждой строке. Если у шага несколько состояний, показывай их отдельными соседними строками; не разбрасывай одинаковый шаг по таблице.
- `Условия`: роль, статус объекта, флаг, данные и другие условия возникновения.
- `Поведение или ограничение`: начинай с наблюдаемого результата для пользователя, затем кратко называй причину в коде или API. Для расхождения используй явную конструкцию `Конфликт: код делает X; тикет требует Y; в Figma показано Z`. Не заменяй описание конфликта одной меткой и не достраивай отсутствующее поведение. Если поведение не найдено, пиши `Не найдено в проверенном коде`.
- `В спеке`: `✅` — точное состояние с теми же условиями и поведением описано и показано в Figma; `⚠️` — описана или показана только часть; `🚫` — состояние отсутствует. После эмоджи всегда кратко указывай, что именно покрыто или отсутствует.
- Каждая ячейка `В спеке` со статусом `✅` или `⚠️` обязана содержать кликабельную Markdown-ссылку вида `[Figma](url)` на точный узел, где показано это состояние. Текст вроде `✅ Отели, авиа и ж/д` без ссылок недопустим. Если состояние показано в нескольких вертикалях или бордах, добавляй отдельную ссылку для каждой: `✅ [Отели](url), [авиа](url), [ж/д](url)`.
- Для `🚫` ссылка не нужна: этот статус означает, что точного состояния на проверенной борде нет. Если точный узел нельзя получить, не ставь `✅` или `⚠️`; укажи, что визуальная часть не проверена.
- `Вопросы`: один вопрос, ответ на который закрывает неизвестное; не предлагай решение.
- `Источник`: для текущего поведения указывай точный `path:line`; для ограничения — строку API-контракта; для целевого требования — тикет; для состояния в спеке — точный узел Figma. В одной ячейке можно перечислить несколько источников.

## Изменения с прошлого запуска

Добавляй, если пользователь передал предыдущую таблицу или она уже есть в контексте текущего запроса. Не ищи прежние Figma-фреймы специально. Основные таблицы должны показывать обновлённое текущее состояние, а этот раздел — только отличия от предыдущей версии.

| ID или состояние | Было | Стало | Источник |
|---|---|---|---|
| … | … | … | Новый тикет, Figma-узел или изменение кода |

Покажи изменения вместе с основными таблицами в чате. Не изменяй прежнюю таблицу или другие элементы в Figma.
