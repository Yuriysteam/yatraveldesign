# Дизайн-система и компоненты

Читать этот файл полностью при создании или аудите продуктовых экранов внутри спеки, выборе organism/Base-компонентов, локальных компонентов, иконок, variants, variables, styles и modes.

До редактирования продукта, выбора component source или аудита `mainComponent`, local duplicates и library provenance полностью прочитать общий навык [Travel Figma Design System](../../travel-figma-design-system/SKILL.md), затем указанные в нём [карту Organisms 2.0](../../travel-figma-design-system/references/organisms20-figma-map.md) и [карту Base 2.0](../../travel-figma-design-system/references/base20-figma-map.md). Для узкого read-only аудита только bindings без выбора компонентов карты можно не открывать. Страницу `🛠️ Кандидаты в организмы от разработки` не использовать.

## Лестница специфичности

Для каждого блока идти сверху вниз:

1. Опубликованный компонент продуктового слоя целевого продукта.
2. Компонент общей Base 2.0.
3. Композиция связанных библиотечных компонентов.
4. Локальный компонент файла.
5. Свободные слои — только когда предыдущие варианты не решают задачу.

Для каждого крупного продуктового блока сначала искать целый organism, а не собирать его из внутренних частей.

## Крупные продуктовые блоки

К ним относятся modal, drawer / side panel, header / navbar, sheet, card / snippet, map, upload, нижняя action-зона и аналогичный самостоятельный wrapper.

Если для роли, продукта и платформы существует подходящий published master:

- корневой узел блока обязан быть linked `INSTANCE` именно этого master;
- внутренние связанные instances внутри внешнего `FRAME`, `GROUP` или локального компонента не делают весь блок библиотечным organism;
- перед передачей проверить `type === INSTANCE`, разрешённый `mainComponent` и library/component key либо другой подтверждённый идентификатор удалённого источника, variant и component properties;
- конфигурировать exposed properties вместо пересборки внутренних частей;
- внутренние иконки не подменять, если нет instance-swap property.

Имя компонента без разрешённого source/key не доказывает provenance: локальная копия может называться так же. Если ссылка на master или remote metadata недоступна, отметить проверку как неполную, а не принимать совпадение имени за linked library source.

Для Экстранета продуктовый компонент имеет приоритет над похожим общим Base-компонентом. Общие токены и базовые контролы всё равно берутся из Base 2.0.

## Договорённости Экстранета

- Для ввода и поиска по умолчанию использовать Base 2.0 `InputOutlined`. `InputSolid` — только при подтверждённом продуктовом паттерне или явном требовании.
- Standalone и swappable-иконки брать из `Travel.Styles` в точном размере slot.
- При наличии семантической альтернативы предпочитать имя с суффиксом `New`.
- Для amenity всегда брать семантически подходящую exact-size иконку `Travel.Styles` с `New` и более тонким рисунком. Не использовать `Bold`, `Heavy`, `Filled` при наличии тонкой альтернативы.
- Размер корневого component frame у asset должен точно совпадать со slot и вариантом `IconContainer`: иконка `24 px` → `IconContainer · XL · 24`. Видимые bounds внутреннего vector не используются как размер asset. Не помещать `24 px` asset в `20 px` container и не скрывать mismatch масштабированием.
- После каждого icon swap проверять semantic color binding принимающего компонента. В пустом input/search leading icon использует `text & icons/secondary`, как placeholder, а не `text & icons/primary`.
- В кнопке «Назад» использовать полную стрелку со штоком, не chevron. Для `24 px` slot — `Icons / 24 / ArrowLongLeftNew`; сохранить semantic icon binding кнопки.
- Для закрытия модалки использовать `Icons / 24 / CloseNewNew` в предусмотренном slot.

## Аудит bindings

| Область | Требование | Что проверить в Figma |
|---|---|---|
| Компонент | Не рисовать копию доступного компонента | `INSTANCE`, `mainComponent`, source library, variant и properties |
| Detach | Только подтверждённое исключение | Нет необоснованных локальных копий библиотеки |
| Цвет | Семантический token/style | Реальный variable binding или published style у fill/stroke/text fill |
| Типографика | Text style или токен ДС | `textStyleId` и/или связанные variables, не только визуальное сходство |
| Отступ | Spacing-токен, если он существует | Binding у padding/itemSpacing, не только совпавшее число |
| Радиус и эффект | Token/style ДС в продуктовом UI | Ручное значение только для spec shell или зафиксированного исключения |
| Иконка | Библиотечный exact-size asset | Корректные library source, slot, размер, поколение и semantic color |
| Mode | Режим целевого продукта/темы | Variables резолвятся в нужном collection mode |

Совпадающий HEX, размер или шрифт не считается токеном без реального binding/style.

Типографика проходит gate, если применён ожидаемый published `textStyleId`. Полный набор official variable bindings допустим без style только когда такая комбинация явно документирована в Base map или воспроизводит bindings актуального published DS-component. Частичный binding при остальных ручных свойствах не считать полной токенизацией; недокументированную variable-only комбинацию отметить как unresolved DS gap, а не принять молча.

## Исключения

В spec-only DS-аудит не разрешает менять утверждённый UI. Унаследованные raw values, detach и другие дефекты исходника записать отдельно от ошибок, внесённых при сборке. Упаковка может быть завершена с перечисленным DS-долгом исходника; полное соответствие ДС при этом не заявлять. Для разрешённого UI-repair проверять результат до/после: variant, тексты, media, размеры, Fill/Hug, переносы, bindings и mode. Токен правильного имени в неверном mode также может дать неверный цвет.

Если нужного компонента или токена нет:

1. Проверить продуктовую библиотеку и Base 2.0.
2. Проверить variants, properties и допустимые instance swaps.
3. Собрать композицию из готовых частей.
4. Только затем создать локальный паттерн.
5. В передаче назвать исключение и причину.

Если семантически правильный master существует, но `UNPUBLISHED`, не импортируется или не разрешается как linked instance:

- назвать блок, ожидаемый master, key/node и причину сбоя;
- не подменять его нерелевантным published component только ради статуса `INSTANCE`;
- в spec-only сохранить утверждённое представление;
- альтернативную локальную композицию делать только в разрешённой смешанной задаче и также пометить как исключение.

Если пользователь уже разрешил конкретный unpublished master, повторно разрешение не запрашивать: проверить доступный способ получить instance с реальной связью именно на него. Разрешение использовать master не разрешает создавать локальный дубликат под его именем. При технической недоступности linkage зафиксировать конкретный gap.

## Локальные компоненты

Создавать local master только после проверки библиотек и хотя бы при одном условии:

- блок повторяется на нескольких экранах;
- у блока есть свои состояния или конфигурация;
- обновления должны синхронно распространяться по спеке;
- это новый продуктовый паттерн, которого нет в библиотеках.

Группа ради перемещения не обязана становиться компонентом. До создания master определить variants/properties, разместить master в явной зоне локальных компонентов и заменить повторения instances, не копиями frame. Если паттерн должен жить за пределами задачи, отдельно поднять вопрос о продуктовой библиотеке.

Сначала проверить уже размещённые пользователем local masters и их потребителей. Повторный проход переиспользует их; менять общий master можно только после проверки, что обновление не затронет несогласованные экраны вне target.

В сборке спеки компонентизация повторяющейся утверждённой композиции — упаковочное действие: она допустима внутри согласованного target при сохранении вида, текстов и поведения. Не требовать отдельного разрешения на каждую такую часть. Новый UX, исправление принятого UI, замена готового DS-master или изменение общих masters с внешними потребителями этим не разрешаются.

### Архитектура: смысловой блок → части → библиотечные controls

Моделировать повторяемое понятие продукта, а не перечень кадров спеки. При нескольких независимых параметрах выделять оси, а не одну ось `State`, перемножающую способ оплаты, конкретное число, ошибку, открытое меню и scroll offset. Параметр, меняющий только вложенный контрол, настраивать там; новый variant всего экрана для этого обычно не нужен.

Проверенный пример: `Policy` в [итоговом Постпэе](postpay-reference-pattern.md) имеет `Payment Type = Online/Postpay/Hybrid` и `Free Cancel = Yes/No`. Внутри — связанные локальные `Free cancellation period`, `End Period`, `Prepayment`, `Count`, а внутри них — instances ДС. Оси описывают реальную конфигурацию; зависимости и допустимость комбинаций всё равно определяет продукт.

Сначала проверить существующие библиотеки, затем создать недостающую продуктовую композицию из linked parts. Такая композиция допустима и не является копией Dropdown или заменой готового Drawer. Если local wrapper содержит published organism, проверить, что его реальные header/body/footer slots используются, а не скрыты и повторены соседними свободными слоями.

Master содержимого по умолчанию использует auto layout и высоту HUG. Фиксированный viewport, clipping и scroll offset принадлежат экрану/scroll-container. Не зашивать их в каждый variant смыслового блока. Фиксированный компонент допустим, если размер — часть его реального контракта.

Свойства экспонировать из потребностей редактирования: семантические variant axes, повторно меняемые тексты, нужные booleans/swaps. Не добавлять API ради количества properties; доступного nested instance может быть достаточно. Не создавать master для каждой одноразовой группы слоёв.

### Каталог локальных компонентов

- Одна строка — продуктовая роль: например, «Способ оплаты», «Правила отмены», «Поясняющий информер».
- Показывать `Мастер` и рядом его `Запчасти`; для двух независимых осей — подписанную матрицу строк и колонок.
- Варианты одинаковой роли выравнивать по верхнему краю, сохраняя естественные высоты и продуктовую поверхность.
- Фоны, иллюстрации, construction templates и полные сценарные снимки не смешивать с основной анатомией продукта. Если они нужны, оставить отдельную явно служебную область.
- Проверить реальные связи `экран → master → local parts → DS`, а не только количество instances. Новый снимок-master с одним потребителем на каждый экран не даёт переиспользования смысловых частей.
- Не объявлять master неиспользуемым по отсутствию прямых instances в одной спеке: он может использоваться вложенно, в шаблонах или за пределами target.

## Отступы продуктового UI

Не переносить значения оболочки спеки внутрь интерфейса.

1. Если spacing встроен в готовый компонент — не переопределять.
2. Если есть продуктовый паттерн — повторить его.
3. Если есть Base spacing token — привязать его.
4. Если правила нет и решение влияет на систему — согласовать.

Не переносить старое числовое правило на весь проект после пользовательской правки. В актуальном `Policy` Постпэя проверены gap `32 px` и padding `28 px`; это свойства конкретного master, а не норма для всех промежутков шторы. До правки выяснить владельца отступа и прочитать его актуальные свойства. Подробности и source nodes — в [разборе примера](postpay-reference-pattern.md).

У `layoutMode = NONE` binding к `itemSpacing` не влияет на раскладку. В таком случае безопасно собрать внутренний auto layout либо выдержать точную геометрию и отметить техническое исключение. После изменения блока проверить все следующие блоки и общую высоту.

## Проверка модуля

- для каждого крупного блока проверен наиболее специфичный published organism;
- linked instances действительно ведут к ожидаемым masters;
- variants, properties и modes корректны;
- цвета, типографика, spacing, radii и effects имеют реальные bindings/styles;
- exact-size icon соответствует slot и сохраняет semantic color;
- нет скрытого detach и локальных masters, дублирующих библиотеку;
- все `UNPUBLISHED` и недоступные assets названы как исключения.

## Формат DS-аудита

Для каждого подтверждённого нарушения вернуть:

- node ID и имя;
- тип нарушения;
- фактическое состояние и проверяемое evidence;
- ожидаемый master/token/style/slot;
- затронутые аналоги;
- классификацию: blocker, некритичное, подтверждённое исключение или unresolved asset gap.

Не придумывать node IDs или нарушения без доступа к target. Отсутствующий точный target блокирует адресный аудит. Недоступные library source, mode или bindings ограничивают только соответствующую проверку; видимые проблемы и подтверждённую геометрию можно проверить отдельно. Не называть весь DS-аудит пройденным при таких gaps.
