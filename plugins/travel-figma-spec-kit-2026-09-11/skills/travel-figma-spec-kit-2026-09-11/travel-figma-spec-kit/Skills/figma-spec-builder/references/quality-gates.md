# Quality gates и передача

Читать этот файл полностью для финального QA, handoff и полного аудита существующей спеки. Для узкой правки проверять изменённые узлы и зависимые от них layout/связи; не требовать нового аудита всего файла.

Для каждой применимой проверки фиксировать результат: **пройдено** (есть evidence), **нарушение**, **не проверено** (нет доступа/данных) или **неприменимо** (с причиной). Критичность нарушения и статус проверки — разные поля. Не считать недоступную проверку пройденной или неприменимой.

Evidence — текущий node ID, прочитанные свойства и/или фактически просмотренный export после последней правки. Назвать scope, дату/сессию и ограничения. Полная готовность возможна только после применимых numeric и visual проверок; структурный валидатор локального skill-пакета не проверяет Figma.

## Gate 1. Содержание

- [ ] Покрыты все сценарии согласованного объёма.
- [ ] У каждого сценария понятны предусловие, реальная точка входа, действие и результат.
- [ ] Последовательность значимых шагов полна; длина ряда не ограничена искусственным числом кадров.
- [ ] Для каждого не начального кадра понятно, из какого действия или системного шага он появился.
- [ ] Существенные ошибки, отмена и подтверждение не пропущены.
- [ ] Loading, empty, disabled и edge cases добавлены только когда меняют реализацию или проверку.
- [ ] Новые ненужные дубли не созданы; существующие пользовательские кадры сохранены, если их удаление не запрошено; различия похожих кадров названы.
- [ ] `Out of scope`, gaps и оставшиеся вопросы обозначены.
- [ ] У состояний есть источник и связь с итоговым node; невозможные состояния отмечены неприменимыми, неизвестные не объявлены исключёнными.
- [ ] «Мало/много» проверяет реальные границы или явно подписанные демонстрационные примеры; подписи соответствуют содержимому.
- [ ] Состояния сгруппированы по понятной продуктовой оси, аналогичные режимы имеют одинаковый порядок колонок; правила находятся рядом с соответствующими кадрами.
- [ ] Каталог и последовательный сценарий не смешаны; количество колонок определяется темой, а не фиксированным шаблоном.
- [ ] Исправленная пользовательская спека имеет приоритет над устаревшим снимком прототипа; наблюдённые баги не выданы за принятые требования.

Норматив: [сценарии, состояния и overlay](scenarios-states-and-overlays.md).

## Gate 2. Стрелки

- [ ] Каждый scenario row линеен; независимые ветки разнесены по отдельным rows.
- [ ] Для каждой связи проверена тройка `source root frame → trigger/hit area, системное событие или подписанная серия действий → next root frame`.
- [ ] Tail касается полного интерактивного container; для системного события или явно подписанной серии действий — границы frame/зоны действия. Arrowhead касается видимого контура следующего root frame.
- [ ] Погрешность каждого endpoint не больше `2 px`.
- [ ] Измерены реальные tail/head в единой системе координат, а не bounds instance; родитель и clipping не скрывают линию.
- [ ] Нет висящих стрелок, пересечений важного контента и неоднозначных источников или целей.
- [ ] При свободном промежутке маршрут прямой или плавный; нет лишнего обхода под экраном ради ограничений готового variant.
- [ ] После последнего move, resize или изменения gap endpoints затронутых стрелок проверены численно и визуально на масштабе не меньше `100%`.

Норматив: [стрелки и маршруты](arrow-routing.md).

## Gate 3. Дизайн-система

- [ ] Для каждого крупного блока проверен наиболее специфичный published organism.
- [ ] Корневой узел доступного organism остаётся linked `INSTANCE`; подтверждены `mainComponent`, source, variant и properties. Совпадение имени не заменяет provenance.
- [ ] Нет необоснованного detach или local master, дублирующего библиотеку.
- [ ] Colors, typography, spacing, radii и effects имеют реальные semantic bindings/styles, где они существуют.
- [ ] Modes соответствуют продукту и теме.
- [ ] Иконки библиотечные, exact-size, соответствуют slot и semantic color; для Extranet соблюдены `Travel.Styles`/`New` conventions.
- [ ] `UNPUBLISHED` и недоступные правильные masters названы как исключения, не подменены нерелевантными components.
- [ ] Local components имеют оправданное переиспользование и используются instances.
- [ ] Local API описывает смысловые части и независимые оси; один `State` не смешивает все снимки сценариев, примеры чисел, меню и scroll offsets.
- [ ] Каталог объясняет «Мастер → Запчасти», а реальные потребители подтверждают переиспользование. HUG-контент отделён от viewport/clipping демонстрации.

В spec-only перечислить унаследованные DS-дефекты утверждённого исходника; их исправление не является условием завершения упаковки и не разрешено самим gate. С такими дефектами не заявлять полное соответствие ДС. В смешанной задаче проверить, что DS-repair не изменил неожиданно surface, переносы, media, icons или actions.

Норматив: [дизайн-система и компоненты](design-system-and-components.md).

## Gate 4. Оболочка

- [ ] Видимая frame-оболочка `[SPEC]` имеет radius `240 px`, если нет прямого исключения; нативной `SECTION` неподдерживаемое свойство не присваивалось.
- [ ] Master `Section List` имеет vertical gap `120 px` между каждой парой соседних scenario rows.
- [ ] Каждый scenario `Section List` имеет radius `120 px` и `Clip content`.
- [ ] Каждый nested `Section` имеет radius `0 px`.
- [ ] Каждый `Section Cover` имеет vertical Fill/Stretch и равен высоте своего row.
- [ ] Индивидуальный `Screen title` совпадает по ширине и X с парным screen frame; подписи помещаются, макеты выровнены по верху общей полосой заголовков или эквивалентной раскладкой.
- [ ] Внешний фон секции — `#000000`; оболочка консистентна с принятой спекой. Product DS-аудит не требует токенизации служебного оформления.
- [ ] После изменений пересчитана цепочка content → scenario row → master list → root layout → `[SPEC]`.
- [ ] Нет наложений, случайных gaps, пустых хвостов и обрезанного content.

Норматив: [Organize и оболочка](organize-and-shell.md).

## Gate 5. Overlay и композиция

- [ ] Штора или модалка показана поверх полного релевантного фонового экрана.
- [ ] Background, overlay и container имеют согласованную высоту.
- [ ] Значимый content и нижние actions не обрезаны.
- [ ] Sticky/fade/scroll показаны намеренно, а не случайным clip.
- [ ] Modal actions и способ выхода понятны.
- [ ] Fullscreen empty/error собран единой центрированной смысловой группой; contextual empty остался в потоке своего блока.
- [ ] На `Section Cover` нет служебных чекбоксов состояний.
- [ ] Изолированные компоненты стоят на читаемой продуктовой подложке; понятно, где они используются.
- [ ] Runtime viewport сохранён; развёрнутый desktop-каталог явно объясняет полное содержимое и реальное scroll-ограничение. Длинный master не заменён случайно прокрученным фрагментом.

Норматив: [сценарии, состояния и overlay](scenarios-states-and-overlays.md).

## Gate 6. Визуальная проверка

Сделать после всех числовых исправлений:

1. Общий screenshot всей `[SPEC]` на малом масштабе — ритм, порядок, пустые зоны, обрезание.
2. Screenshot каждого scenario row на рабочем масштабе — читаемость шагов, titles, arrows, overlays.
3. Крупный screenshot проблемных мест — spacing, icon slot, поверхность, переносы, sticky/scroll. Bindings проверяются свойствами, не screenshot.
4. Сравнение повторяющихся элементов между состояниями.
5. Финальный screenshot после последнего пересчёта layout.

Визуальное сходство не заменяет проверку свойств Figma, а числовая корректность не заменяет итоговый просмотр.

Для стрелок и мелких controls просмотреть детали не мельче `1:1` в дизайн-пикселях. При недоступном export использовать доступный просмотр canvas; если визуальной проверки нет, честно указать «численно проверено, visual QA не выполнен» по ограничениям ядра. Это допустимый отчёт о частичном результате, а не полный handoff.

## Gate 7. Достаточность и handoff

Без устных пояснений читатель должен ответить:

- кто и при каком условии входит в сценарий;
- что пользователь делает;
- какие ветки и ошибки входят в задачу;
- что меняется между соседними кадрами;
- где сценарий завершается или возвращается;
- какое поведение нельзя понять из статичного кадра;
- какие components системные, а какие local;
- что готово, спорно и исключено.

Передача содержит прямую ссылку на существующий итоговый node, покрытие, изменения и применимые DS/local замечания, исключения, gaps и вопросы. Если запись была недоступна, дать подготовленные материалы и указать, что Figma не изменена. Непроверенный target не называть проверенным. Если ответы уже есть, дальнейшее описание очевидных деталей не улучшает спеку.

## Классификация замечаний

- **Blocker** — невозможно однозначно реализовать или проверить затронутую часть; нарушена логика, вход/результат, необходимый linked component, критичный overlay либо геометрия скрывает content. Назвать, что именно блокируется; остальные подтверждённые части можно закончить.
- **Некритичное** — не меняет реализацию, но ухудшает чтение, ритм или гигиену файла.
- **Исключение** — осознанное отклонение с причиной и владельцем решения.
- **Вопрос** — неизвестный ответ меняет продуктовую логику, конечный экран, сохранение данных, права или состав состояний.
- **Не проверено** — отсутствует evidence; это статус проверки, не подтверждённый дефект. Указать недостающий доступ/данные и следующий шаг.

## Антипаттерны

- `Draft spec` без прямого запроса.
- Скрытый редизайн в spec-only задаче.
- Копия DS-компонента или detach ради удобства.
- Ручной цвет, шрифт или spacing в продуктовом UI при доступном binding, если нет принятого исключения. Служебное оформление спеки проверяется по отдельному shell-правилу.
- Исправленный один пример при оставшихся старых аналогах.
- Фиксированная высота `Section Cover`.
- Узкий individual `Screen title`, вызывающий случайный перенос.
- Radius у nested `Section` вместо внешнего scenario `Section List`.
- Выключенный clip, скрывающий ошибку shell.
- Обрезанная штора, невидимый фон или нижние actions.
- Случайный clip, выданный за scroll.
- Комбинаторный взрыв состояний.
- Стрелки между независимыми состояниями или несколько исходящих веток из одного кадра.
- Начало стрелки у glyph/label вместо полного hit area.
- Стрелки, поставленные до финального layout и не проверенные после его изменения.
- Длинное пояснение, которое ничего не меняет для реализации или QA.
- Полные снимки сценариев как единственная архитектура local components.
- Раздробление одного режима по многим секциям ради трёх колонок.
- Дублирование правил в cover, подписи и финальном справочнике.
- Заявление о полной готовности без numeric inspection и финального visual QA.
