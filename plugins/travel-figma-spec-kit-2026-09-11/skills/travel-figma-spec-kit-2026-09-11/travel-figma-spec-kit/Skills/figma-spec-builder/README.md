# Figma Spec Builder — командный пакет

Внутренний навык Travel Design для сборки, улучшения и аудита рабочих Figma-спек. Он отделяет упаковку принятого решения от создания макетов, выбирает глубину по риску задачи и последовательно проверяет сценарии, состояния, Organize shell, arrows и дизайн-систему.

Продуктовое проектирование и создание экранов остаётся зоной отдельного навыка `figma-design-machine`; `figma-spec-builder` подключается после фиксации решения либо вторым этапом смешанной задачи.

## Что входит

```text
figma-spec-builder/
├── SKILL.md                         вход и routing
├── references/
│   ├── figma-spec-sufficiency.md    обязательное короткое ядро
│   ├── organize-and-shell.md        Organize и геометрия оболочки
│   ├── scenarios-states-and-overlays.md
│   ├── arrow-routing.md             точные связи trigger → frame
│   ├── design-system-and-components.md
│   ├── workflow.md                  порядок записи
│   ├── quality-gates.md             handoff и аудит
│   └── postpay-reference-pattern.md проверенный итоговый пример пользователя
├── scripts/
│   ├── install.sh                   безопасное подключение команде
│   ├── validate.sh                  поиск Node runtime и запуск проверки
│   └── validate-package.mjs         локальная проверка релиза
├── agents/openai.yaml
├── tests/                          изолированные проверки и поведенческие кейсы
└── CHANGELOG.md
```

`SKILL.md` всегда подключает обязательное ядро. Остальные references читаются только по сигналам задачи, поэтому узкий аудит стрелок не тянет весь документ, а полная сборка получает полный процесс.

## Требования

- Codex Desktop с Figma integration и навыками `figma:figma-use`, `figma:figma-generate-design`.
- Edit-доступ к целевому Figma-файлу.
- View/import-доступ к Organize, Base 2.0, Organisms 2.0, Travel.Styles и продуктовой библиотеке задачи.
- Соседний `travel-figma-design-system`: в нём живут переносимые правила и карты Organisms/Base.
- Соседний `figma-design-machine` для продуктовых макетов и смешанных задач.
- Соседний `yandex-travel-ux-writing` для генерации и ревью нового UX-текста. Его методология, ToV и редполитика входят в пакет; Python-скрипты и отдельный навык `ux-writing` не нужны. Для утверждённых текстов редактор не подключается.
- Wiki, Tracker и browser/product access — когда конкретная задача требует этих источников.

Папка `figma-spec-builder` не является полностью автономной: передавайте четыре соседних навыка — `figma-spec-builder`, `figma-design-machine`, `travel-figma-design-system` и `yandex-travel-ux-writing`. Большой workspace-навык `design` больше не нужен.

## Установка из общей папки

Из корня общей папки Travel Design:

```sh
bash Skills/figma-spec-builder/scripts/install.sh
```

Установщик сначала валидирует весь набор и все конфликты, затем создаёт ссылки на четыре навыка в `~/.codex/skills`. Ничего не удаляется и не перезаписывается: при отличающемся существующем пакете установка останавливается до изменений. Совместимую обычную копию companion-навыка он оставляет на месте только при полном совпадении файлов, включая references; symlink и специальные файлы внутри копии не принимаются. В конце отдельно сообщает, найдены ли prerequisite skills Figma integration. Это ещё не доказывает доступность записи или библиотек в текущей сессии.

После установки открыть новую задачу Codex. Если каталог навыков не обновился, перезапустить приложение.

## Как использовать

Явный вызов удобен для предсказуемого командного результата:

```text
$figma-spec-builder Проверь утверждённые мобильные макеты и собери спеку в node …
```

Навык также срабатывает автоматически на запросы «собери спеку», «доработай спеку», «проверь спеку» и «проведи handoff-аудит». Полезно сразу передать:

- source и target Figma nodes;
- продукт, platform и role;
- что уже утверждено и что разрешено менять;
- ссылку на требования, prototype, Wiki или Tracker;
- известный `out of scope`.

Если пользователь просит также изменить продуктовые макеты, навык классифицирует задачу как смешанную и сначала фиксирует актуальное решение, затем собирает спеку.

Запрос на недостающие состояния тоже разрешает дорисовать эти состояния: заново разрешать каждую такую правку не требуется. Неизвестные продуктовые условия уточняются отдельно, подтверждённые части продолжаются. Отдельный Codex-проект не обязателен; для долгой задачи хранить бриф и принятые решения в файлах проекта, а новые задачи запускать с явными source/target-ссылками.

## Проверки после изменений

Структура и переносимость пакета:

```sh
bash Skills/figma-spec-builder/scripts/validate.sh
```

Структура и изолированные регрессионные тесты validator/installer:

```sh
bash Skills/figma-spec-builder/scripts/validate.sh --tests
```

Скрипт сам находит Node.js, включая bundled runtime Codex. Тесты работают с копиями во временных каталогах. Качество решений проверяется отдельно по [поведенческим кейсам](tests/behavior-cases.md); инструкции прогона и критерии находятся в этом файле. Текстовый прогон не заменяет проверку на живом Figma-target с реальными библиотеками, bindings и финальными screenshots.

## Обновление

При установке через symlink изменения общей папки приходят автоматически. Новая задача Codex перечитывает актуальную версию навыка.

Для будущего Git-источника рекомендуемый процесс: `git pull --ff-only`, новая задача Codex, затем короткая smoke-проверка. Не поддерживать отдельную отредактированную копию в `~/.codex/skills`.

## Изменение навыка командой

1. Редактировать каноническую папку `Skills/figma-spec-builder`, а не установленную копию.
2. Одно правило хранить в одном нормативном reference; quality gates должны ссылаться на него, а не повторять алгоритм целиком.
3. Обновить `metadata.version`, `metadata.updated` и верхнюю запись `CHANGELOG.md` вместе.
4. Запустить:

```sh
bash Skills/figma-spec-builder/scripts/validate.sh
```

5. Проверить затронутые маршруты по [поведенческим кейсам](tests/behavior-cases.md); для релиза — весь набор и отдельный live smoke на согласованном Figma-target. В отчёте разделить текстовую и живую проверку.
6. Отдать изменение на review владельцу Travel Design.

Новые проектные правила помечать как проектные, а не превращать в универсальные. Component keys и названия сверять с актуальными DS-картами перед релизом.
