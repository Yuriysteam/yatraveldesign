# Figma Design Machine — роутер

Выбрать нужный процесс, передать его профильному скиллу и довести до результата, который запросил пользователь. Роутер отвечает за выбор и завершённость маршрута; правила продуктового решения, дизайн-системы, текста и оформления остаются у профильных скиллов.

## Вход и приоритет

Из запроса и доступного контекста определить **исходник → результат → разрешённое изменение**. Исходником могут быть задача/требования, HTML-прототип, Figma-макеты или существующая спека. Результатом — макеты, спека, аудит или текст. Одного слова «Figma» недостаточно для запуска полного процесса.

Если пользователь явно вызвал профильный скилл, продолжить через него и только его нужные зависимости. Не подменять такой вызов общей сборкой. При явном вызове нескольких скиллов сохранить выбранные пользователем этапы и порядок, если они совместимы; уточнить только реальный конфликт. Прямые вызовы профильных скиллов работают без роутера.

Явный профильный вызов — `$figma-design-machine` либо указание вроде «используй скилл figma-design-machine». Само название комплекта «Figma Design Machine» в обычном запросе не закрепляет ведущим одноимённый профильный скилл: маршрут выбирается по исходнику и результату. Явный `$figma-workflow-router` всегда обращается к этому роутеру.

Для общего запроса вроде «Figma Design Machine, подготовь это к разработке» выбрать маршрут ниже. Если неясно, нужен ли новый дизайн, перенос принятого решения или только оформление, сначала выяснить это по источникам. При оставшейся неопределённости задать один вопрос о конечном результате; независимый разбор источника продолжать. Название комплекта не является разрешением на редизайн.

## Выбор ведущего скилла

Прочитать выбранный `SKILL.md` и его обязательные references. Остальные скиллы загружать по условиям работы, не все одновременно.

| Запрос и состояние исходника | Ведущий скилл | Граница результата |
|---|---|---|
| Перенести HTML-прототип в Figma, со спекой или только макетами | [html-to-figma-spec](../html-to-figma-spec/SKILL.md) | Передать точный deliverable: для макетов закончить после их QA; для спеки продолжить к сборщику внутри этого процесса |
| Собрать, дополнить или проверить спеку из существующих Figma-макетов | [figma-spec-builder](../figma-spec-builder/SKILL.md) | Сценарии, состояния, упаковка и проверки в согласованном target |
| Сначала создать/исправить макеты, затем собрать спеку; исходник — задача или Figma | [figma-spec-builder](../figma-spec-builder/SKILL.md), смешанный режим | Ведущий координирует `figma-design-machine` для макетов, затем завершает спеку |
| Создать/исправить только макеты или предложить концепции | [figma-design-machine](../figma-design-machine/SKILL.md) | Макеты и их проверки; не добавлять спеку без запроса |
| Проверить только компоненты, токены, иконки или происхождение product UI | [travel-figma-design-system](../travel-figma-design-system/SKILL.md) | Адресный DS-аудит; изменения только в запрошенном объёме |
| Написать, улучшить или проверить только интерфейсные тексты | [yandex-travel-ux-writing](../yandex-travel-ux-writing/SKILL.md) | Текст/редакторский аудит; Figma нужен только если пользователь просит правку в файле |

Когда есть HTML и уже проверенные восстановленные Figma-кадры, исходник следующего этапа — эти кадры. Если пользователь просит только их упаковку, перейти сразу к `figma-spec-builder`; повторный импорт HTML не нужен. HTML как дополнительный reference для проверки готовой спеки также не превращает задачу в полный перенос.

Задачи вне этой таблицы, например Figma → HTML или создание библиотеки, передавать доступному соответствующему скиллу по его описанию. Не расширять комплект и не устанавливать плагины автоматически ради совпавшего слова.

## Когда подключать общие правила

- **Дизайн-система:** при выборе/изменении product UI или аудите его компонентов ведущий читает `travel-figma-design-system` до сборки и проверяет результат по его правилам. Узкая правка стрелок, обложек или раскладки спеки следует профильному reference сборщика; сама по себе она не требует нового DS-аудита всего продукта.
- **Редактор:** при создании или изменении UX-текста применить `yandex-travel-ux-writing` в рамках текущего этапа до окончательной раскладки. Его методология, ToV и редполитика включены в скилл; отдельные `ux-writing` и `store` не нужны. Для утверждённых текстов сохранять исходник; явный запрос редакторского аудита разрешает проверку, но сам по себе не разрешает переписать всё на канвасе.
- **Figma-инструменты:** ведущий читает актуальные навыки Figma-интеграции и проверяет доступные операции перед работой с файлом. Для локального разбора HTML, редактирования переданных строк или планирования маршрута соединение Figma не является предварительным условием.
- **Контекст Travel:** следовать правилам проекта и его источникам. Не переносить продуктовые факты в роутер или в общий командный архив.

Эти зависимости применяет агент в текущей задаче. Скилл не создаёт отдельного агента автоматически. Если нужен независимый reviewer и доступна делегация, ему можно передать ограниченный аудит; запись в один и тот же Figma-target остаётся у одного исполнителя.

## Один маршрут и передача результата

В начале коротко назвать пользователю выбранную последовательность и причину. Для многоэтапной задачи держать компактную запись в текущем плане или существующем worklog: `исходник → результат; ведущий; этапы и статус; подтверждённые nodes; нерешённые вопросы`. Не заводить отдельную инфраструктуру для точечной правки.

На переходе передать: актуальный source/target, принятые решения и разрешённые изменения, итоговые frame/node IDs, найденные component mappings, покрытие сценариев/состояний и gaps. Переход к следующему уже запрошенному этапу не требует повторного разрешения.

Для макетов, созданных или изменённых в текущей цепочке, завершить предусмотренные numeric/visual проверки до передачи в сборку спеки. Упоминание сборщика внутри профильного скилла не переносит этот переход раньше завершения QA макетов. Если часть проверки недоступна, явно передать её статус и выполнять только допустимую независимую работу по правилам ведущего; не объявлять результат полностью проверенным.

**Не запускать второй параллельный процесс сборки:** если `html-to-figma-spec` уже ведёт перенос и затем вызывает сборщик, роутер наблюдает завершение этой цепочки. Если сборщик в смешанном режиме привлёк создание макетов, после них вернуться к незавершённому этапу спеки, не начинать новую спеку из-за ссылки на неё в `figma-design-machine`. Уже прочитанные правила и выполненные проверки не повторять без изменения результата или выявленного пробела.

При продолжении сохранять контекст, завершённые этапы и ведущего ещё активного этапа. Если этап уже завершён, выбрать ведущего следующего этапа по актуальному исходнику: проверенные восстановленные кадры → сборщик спеки. Перестроить только затронутую часть маршрута, если пользователь изменил результат, границы или исходник. Профильные скиллы не должны вызывать роутер обратно; зависимости направлены от роутера к исполнителям.

Если отсутствует нужный скилл, инструмент или подтверждённое поведение, назвать конкретный пробел и выполнить доступную независимую часть. Не считать отсутствие необязательного для этой задачи скилла блокером. Неизвестное сохранение, права, backend-ошибку или намеренное отличие от продукта не решать предположением; приостановить только зависимую часть.

## Завершение

Проверки результата принадлежат ведущему: для макетов — его numeric/visual QA, для спеки — quality gates сборщика, для узкого аудита — проверка затронутой области, для текста — правила редактора. Роутер проверяет, что все запрошенные этапы завершены либо имеют явно названный blocker; дублирующий всеобщий аудит не нужен.

Вернуть фактический результат и ссылки, покрытие и оставшиеся ограничения. Различать план, статический разбор, готовые макеты и готовую спеку. Успешный выбор маршрута или локальная проверка пакета не подтверждают запись и качество результата в Figma.
