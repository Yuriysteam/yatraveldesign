## Пример чекаута — evidence, не норматив объёма

[Рабочая спека чекаута](https://www.figma.com/design/COAuahp5VtqYloSIKLLeh9/Новый-чекаут-ч.2?node-id=29-46337) содержит 11 смысловых строк и 68 подписанных колонок:

- 2 каталога состояний;
- 7 сценариев;
- 2 коротких блока с правилами подскролла.

Её детализация вызвана количеством платёжных методов, backend-ошибок и критичностью чекаута. Это не минимальный объём для любой задачи.

Полезные наблюдения:

- состояния раскрыты подробно, когда каждое из них меняет проверяемое поведение;
- сценарии показывают только значимые шаги;
- qualifier добавляется, когда одинаковый UI имеет разные условия;
- независимые каталоги состояний не соединяются стрелками;
- Light и Dark стоят рядом только там, где это добавляет решение;
- отдельный короткий пример допустим, когда статичный финальный кадр не объясняет scroll или другое взаимодействие.

## Иерархия

В формате используются два уровня с именем `Section List`:

- **master `Section List`** — вертикальный список scenario rows;
- **scenario `Section List`** — внешняя скруглённая оболочка одной горизонтальной строки.

Не выбирать узел только по имени. Master определяется как вертикальный родитель строк; scenario `Section List` — его непосредственный ребёнок. Горизонтальную раскладку внутри scenario-контейнера выполняет вложенный `Section`.

```text
[SPEC] Название задачи — платформа                    FRAME, radius 240
└── Root layout                                       FRAME
    ├── Name / служебная шапка
    └── Section List                                  master, VERTICAL, gap 120
        ├── Section List                              scenario, radius 120, clip
        │   └── Section                               HORIZONTAL, radius 0
        │       ├── Section Cover                     vertical FILL / STRETCH
        │       └── Screens / Content
        │           ├── Screen title
        │           └── [STATE] Состояние
        ├── Section List
        └── …
```

Ответственность уровней:

- `[SPEC]` объединяет одну задачу и согласованную область передачи;
- `Root layout` задаёт внешние поля, шапку и расстояние до контента;
- master `Section List` управляет вертикальным ритмом;
- scenario `Section List` владеет видимым скруглением и clip;
- вложенный `Section` раскладывает cover и content по горизонтали;
- `Section Cover` называет сценарий, условие или каталог;
- `Screens / Content` содержит кадры, подписи, связи и пояснения.

Имя «секция спеки» не задаёт нативный тип `SECTION`. Для новой скруглённой оболочки использовать `FRAME`. У нативного `SectionNode` в Plugin API нет `cornerRadius`; он может оставаться внешним организационным родителем, а radius `240` принадлежит видимой frame-оболочке. В существующем файле сначала найти фактического владельца заливки и скругления, не заменять пользовательский контейнер только из-за схемы. Проверка API: [SectionNode](https://developers.figma.com/docs/plugins/api/SectionNode/).

Несвязанные сценарии не объединять в одну строку ради экономии места.

## Ширина, заголовки и визуальный ритм

Для каталога выбрать ширину по содержимому самой насыщенной смысловой строки. Не дробить одну тему на много вертикальных секций ради фиксированных двух-трёх экранов в ряд. Сохранить общие ширины строк, одинаковые начала колонок и выравнивание верхнего края макетов; свободное место в более короткой строке допустимо.

В сравнительных каталогах предпочтителен общий `Title section` над `Content`: заголовок и макет каждой колонки имеют одинаковые X и ширину. Длинная подпись увеличивает общую полосу заголовков, а не сдвигает один макет вниз. Эквивалентные column wrappers допустимы, если сохраняют это выравнивание. Не копировать случайную фиксированную высоту или переполнение контейнера из примера.

Внешний фон секции — `#000000`; подложка смысловых строк соответствует принятой тёмной оболочке. Правила ДС для продуктовых экранов не распространяются автоматически на служебную типографику, линии и поля спеки. Там важны иерархия и консистентность с соседними спеками; ручные значения допустимы. Не менять продуктовые colors/modes ради оформления оболочки.

В [итоговом Постпэе](postpay-reference-pattern.md) проверен ритм `200 px` вокруг Screens, `350 px` между колонками и `100 px` между полосой заголовков и Content. Это параметры данного оформления, а не spacing-токены продуктового UI. При продолжении того же каталога воспроизводить их; в другом формате сначала прочитать локальный пример.

## Геометрия оболочки

Эти значения относятся к оболочке спеки, а не к продуктовым карточкам внутри макетов.

| Где | Норматив | Проверка | Исключение |
|---|---|---|---|
| Видимая оболочка `[SPEC]` | Радиус `240 px` на всех углах | Числа у frame-владельца скругления, не у нативной `SECTION` | Только прямое решение пользователя |
| Master `Section List` | Vertical gap между scenario rows `120 px` | `itemSpacing = 120` и измеренные gaps | Только явно согласованный другой ритм |
| Scenario `Section List` | Радиус `120 px`, `Clip content` включён | Проверить каждую строку | Только прямое решение пользователя |
| Вложенный `Section` | Радиус `0 px` | Видимое скругление принадлежит внешней оболочке | Нет при этой структуре |
| `Section Cover` | Vertical `FILL`, результат `layoutAlign = STRETCH` | После изменения контента cover равен высоте строки | Только отдельно согласованная короткая обложка |
| `Screen title` над одним экраном | Ширина равна парному screen frame; horizontal `FIXED`, высота по содержимому или общей полосе заголовков; внутренние `Name` и `Description` — `FILL` | Совпадают ширина/X; текст не обрезан, макеты выровнены сверху | Групповой заголовок может охватывать несколько экранов |
| Фиксированный container | Высота пересчитана после изменения контента | Последний ребёнок + нижнее поле совпадают с границей | Hug пересчитывается автоматически, но проверяется визуально |

Не задавать `Section Cover` фиксированную высоту. После изменения gap, высоты экрана или состава строки пересчитать всю цепочку:

```text
content → scenario Section List → master Section List → Root layout → [SPEC]
```

Не оставлять пустой хвост от старой высоты и не обрезать последний сценарий.

Названия `Section`/`Section List` описывают ответственность, а не обязательную пересборку уже корректной иерархии. Для auto layout проверять поведение Fill/Stretch после роста контента, а не только отдельный флаг. `Screen title` не масштабировать вместе с продуктовым экраном ради уместившейся строки.

## Проверка оболочки

- `[SPEC]`: радиус `240`;
- master list: gap `120` между каждой парой соседних rows;
- scenario list: радиус `120` и clip;
- nested `Section`: радиус `0`;
- каждый `Section Cover`: vertical Fill/Stretch;
- каждый индивидуальный `Screen title`: ширина парного экрана;
- родительские высоты пересчитаны;
- нет наложений, случайных gaps, пустых хвостов и обрезанного содержимого.
