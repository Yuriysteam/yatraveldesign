# Стрелки и маршруты сценариев

Читать этот файл полностью, когда нужно добавить, исправить или проверить стрелки, а также после перемещения или resize кадров в ряду, где уже есть стрелки.

Стрелка — точная запись перехода, а не декоративная линия. Она не нужна в каталоге независимых состояний.

## Когда нужна стрелка

- последовательность нельзя уверенно прочитать слева направо;
- действие влияет на другой кадр;
- есть неочевидный возврат, системный или внешний переход;
- без связи разработчик или QA может выбрать неверный источник либо результат.

Не рисовать висящую стрелку, если следующего кадра в границах задачи нет. Результат кратко описать в подписи или аннотации.

## Линейность сценарного ряда

- Один scenario `Section List` показывает один линейный путь слева направо.
- Количество кадров не фиксировано. Для `N` кадров обычно требуется `N − 1` последовательных переходов.
- Первый кадр показывает реальную точку входа или состояние непосредственно перед первым действием.
- Каждый следующий кадр должен иметь понятный вход из предыдущего.
- Из одного кадра не вести несколько стрелок к независимым результатам.
- Каждую продуктовую ветку оформлять отдельным scenario `Section List`, при необходимости повторяя общий исходный кадр. Условие ветки назвать на `Section Cover` или в подписи.
- Не превращать независимые ветки в искусственную цепочку и не сокращать многошаговый путь, если пропадает значимый вход, действие, системный шаг или проверяемое состояние.
- Возврат показывать только тогда, когда без него нельзя понять реализацию или проверку.

## Обязательная модель связи

До рисования для каждой стрелки зафиксировать тройку:

```text
исходный root frame → фактический trigger / hit area → следующий root frame
```

Если любой элемент нельзя назвать однозначно, стрелку пока не ставить: сначала уточнить сценарий или выбрать правильные кадры.

Для системного перехода или кадра, суммирующего серию однотипных действий, вместо одного trigger записать событие/серию и границу исходного frame. Явный CTA этим исключением не заменять. Для возврата повторить экран результата следующим кадром справа: не замыкать ряд обратной стрелкой и не создавать ветвление.

## Координаты и родитель стрелки

- До записи получить актуальные IDs source, trigger (либо подписанный frame-anchor), target и arrow; после дублирования кадров использовать IDs копий в target, не исходников.
- Все расчёты выполнять в одной системе координат страницы Figma, в дизайн-пикселях. `x/y` дочерних узлов относятся к разным родителям: их нельзя сравнивать напрямую или подставлять экранные пиксели screenshot.
- Для обычных неповёрнутых узлов использовать проверенные absolute bounds. Для повёрнутых, масштабированных или отражённых узлов преобразовать локальные anchors через `absoluteTransform`; bounds прямоугольника вокруг поворота не являются видимыми гранями.
- Для записи в координатах host преобразовать точки обратно: `p_host = inverse(T_host) × p_page`. Для чтения фактических концов линии применить её transform в координаты страницы.
- Arrow разместить в общем контейнере сценария поверх экранов, вне clipped product frame. В auto layout стрелка не участвует в потоке; использовать поддерживаемое absolute positioning. Не выключать clip экрана или радиусы/clip оболочки, чтобы показать стрелку.
- Проверить весь маршрут на clipping у предков и достаточные bounds host. Начало внутри исходного экрана должно оставаться видно поверх него.
- Bounds instance `Arrows` могут включать padding и не совпадать с линией. Измерять действительный tail и кончик arrowhead по доступной геометрии и визуальному виду; ширина instance сама по себе ничего не доказывает.

## Порядок расстановки

1. Окончательно выставить размеры и координаты экранов, `Screen title` и gaps.
2. Для каждого перехода выбрать точный trigger в предыдущем кадре (либо разрешённый выше подписанный frame-anchor) и корневой `[STATE]` или screen frame результата.
3. Найти существующую стрелку для той же пары и действия; править её in place. Новую связь создавать только если её ещё нет. Organize `Arrows` использовать, когда его геометрия подходит; допустим редактируемый vector в стиле принятой оболочки. Не дублировать стрелки при повторном запуске и не выдавать vector за library instance.
4. После любого move, resize, изменения gap или пересборки auto layout заново проверить обе точки каждой затронутой стрелки.

Стрелки ставятся после финальной раскладки кадров, а не до неё.

## Точка начала

- Tail лежит на границе **полного интерактивного hit area**, запускающего именно этот переход: button container, icon-button container, кликабельная строка, карточка, ссылка, switch или другой trigger.
- Не привязывать tail к glyph, label или декоративному слою, если кликабельным является внешний контейнер. Для icon-button используется граница кнопки, а не граница иконки внутри неё.
- Для перехода вправо базовая точка — середина правой грани hit area; влево — середина левой; вниз или вверх — середина соответствующей грани. Другую точку той же грани выбирать только для обхода препятствия.
- Tail касается границы hit area или заходит внутрь не более чем на `2 px`. Видимого зазора быть не должно.
- Не начинать стрелку от границы всего исходного экрана, `Screen title` или ближайшего удобного слоя, если есть конкретное действие пользователя.

Если переход запускается системным событием, таймаутом, успешным ответом или жестом без отдельного контрола, не придумывать click target. Подписать событие; начать стрелку от ближайшей границы исходного frame или обозначенной зоны жеста.

Если кадр сжимает серию однотипных действий (например, «выбрал несколько объектов»), допустима прямая связь от границы предыдущего кадра с явной подписью действия. Не привязывать такую связь к произвольному одному checkbox. Это исключение не применяется к явному нажатию CTA: для «Сохранить» или «Применить» исходником остаётся полный hit area кнопки.

## Точка окончания

- Arrowhead заканчивается на видимой границе **корневого следующего `[STATE]` или screen frame**, не на `Screen title`, scenario wrapper, модалке внутри кадра или случайном внутреннем слое.
- Выбирать ближайшую к source facing edge: у кадра справа — левую, слева — правую, ниже — верхнюю, выше — нижнюю.
- Наконечник касается target frame или заходит внутрь не более чем на `2 px`.
- Не оставлять наконечник в межэкранном зазоре, не уводить его в контент и не проводить дальше противоположной границы.
- Если source по вертикали попадает в высоту target и путь свободен, сохранять тот же `Y`: связь читается как прямая горизонталь.

У скруглённого экрана попадание в bounding box около угла ещё не означает касание видимой границы. Выбрать точку на прямой части грани либо проверить фактический контур; при необходимости изменить маршрут. Не заканчивать стрелку в прозрачном углу.

## Маршрут

- Один переход — одна стрелка. Наконечник всегда у следующего кадра; проверить, что instance не развёрнут задом наперёд.
- При одинаковом Y anchors и свободном пути использовать прямую стрелку. При разной высоте source и target предпочитать одну плавную S-кривую в межэкранном промежутке. Ломаная нужна при реальном препятствии; не уводить маршрут под весь экран и обратно, если короткая кривая решает переход.
- Изгибы проходят по свободному пространству. Линия не пересекает нерелевантный экран, `Screen title`, важный контент, другую стрелку и не указывает на соседний control.
- Не отрывать начало от настоящего trigger ради композиции. Если чистый маршрут невозможен, сначала увеличить gap или переставить кадры внутри scenario row.
- Если пользователь заморозил layout, кадры и gaps не менять: подобрать штатный variant либо точный vector-маршрут в принятом стиле оболочки.
- Недостаток вариантов Organize сам по себе не blocker: свободная геометрия допустима для оформления спеки. Сохранить единые stroke/color, направление, tail/head и точность endpoints; не detaching библиотечный instance. Если любой точный маршрут пересекает значимый контент, пересмотреть раскладку в разрешённой области либо обозначить конкретный конфликт.

## Числовая проверка

Для перехода вправо между неповёрнутыми узлами при absolute bounds trigger `(x, y, width, height)` и target frame `(nextX, nextY, nextWidth, nextHeight)` проверить:

- `x + width − 2 ≤ startX ≤ x + width` — касание или до `2 px` внутрь, не зазор снаружи;
- `startY ∈ [y, y + height]`, по умолчанию `startY = y + height / 2`;
- `nextX ≤ endX ≤ nextX + 2` — касание или до `2 px` внутрь target;
- `endY ∈ [nextY, nextY + nextHeight]`;
- arrowhead расположен у `end`, tail — у `start`.

Для переходов влево, вверх и вниз применяется то же правило к соответствующим facing edges.

Пример: absolute hit area `(420, 820, 60, 40)`, target `(850, 100, 400, 800)` → tail `(480, 840)`, head `(850, 840)`. После сдвига target на `120 px` вправо head становится `(970, 840)`; если из сдвинутого экрана выходит другая стрелка, её tail тоже пересчитывается. Это пример вычисления, а не координаты для реального файла.

Для затронутых переходов сохранить краткий результат: `arrow ID → source/trigger/target IDs → измеренные tail/head → отклонение → visual QA`. Если геометрия концов недоступна, числовой статус — «не проверено»; не выводить `≤ 2 px` из сходства на screenshot.

## Визуальная проверка

После числовой проверки открыть каждый сценарий на масштабе не меньше `100%` и подтвердить:

- линия явно выходит из нужного интерактивного элемента;
- наконечник касается конкретного следующего root frame;
- соседний control или экран нельзя прочитать как источник или цель;
- маршрут не пересекает значимый контент;
- после последнего изменения layout endpoints проверены заново.

Для export проверять детали с плотностью не ниже одного пикселя изображения на один дизайн-пиксель. Общий уменьшенный screenshot ряда не подходит для проверки `2 px`. Если ни export, ни просмотр canvas недоступны, применить ограничения из ядра; числовая правка не получает статус полного visual QA.
