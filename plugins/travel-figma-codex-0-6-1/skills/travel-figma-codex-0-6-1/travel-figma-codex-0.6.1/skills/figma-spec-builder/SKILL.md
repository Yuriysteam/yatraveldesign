# Сборщик Figma-спек

Упаковывать принятое продуктовое решение так, чтобы разработчик и QA восстановили сценарии, состояния и границы задачи без устных догадок.

## Граница навыка

Использовать для:

- новой, существующей или неполной Figma-спеки;
- декомпозиции готовых макетов на сценарии и каталоги состояний;
- релевантных loading, empty, error, disabled и edge cases;
- Organize shell, arrows, overlays, DS-аудита и final handoff;
- смешанной задачи, когда пользователь явно просит сначала исправить макеты.

В spec-only не менять продуктовую логику, UX-текст или интерфейс. Разрешены упаковочные действия внутри target: дублирование, перемещение, grouping, naming, annotations, arrows и компонентизация повторяющейся утверждённой композиции без изменения её вида/поведения. Границы общих masters — в DS-reference. Для смешанной задачи порядок: **макеты → зафиксированное решение → спека**.

Создание и продуктовая доработка макетов принадлежат отдельному `figma-design-machine`; этот навык отвечает за последующую упаковку решения и может координировать оба этапа в смешанном запросе.

Запрос «добавь/проработай состояния» разрешает дорисовать эти состояния в границах принятой логики: использовать смешанный режим только для недостающих макетов. Не требовать повторного разрешения на уже запрошенную работу. Неизвестное продуктовое поведение при этом остаётся вопросом, а не фактом.

## Обязательное чтение и маршрутизация

1. Всегда полностью прочитать [ядро достаточности](references/figma-spec-sufficiency.md).
2. По его routing table полностью прочитать каждый reference, относящийся к задаче:
   - [Organize и shell](references/organize-and-shell.md);
   - [сценарии, states и overlay](references/scenarios-states-and-overlays.md);
   - [arrows](references/arrow-routing.md);
   - [дизайн-система и components](references/design-system-and-components.md);
   - [workflow записи](references/workflow.md);
   - [quality gates](references/quality-gates.md).
3. До операций с Figma прочитать доступный `figma:figma-use`; для записи также `figma:figma-generate-design`. Проверить фактически доступные чтение, запись и визуальную проверку по ядру. Наличие навыка не доказывает подключение инструмента.
4. При редактировании product UI или аудите component provenance прочитать соседний `travel-figma-design-system` и его Organisms/Base maps по условиям DS-reference. Для нового UX-текста подключить `yandex-travel-ux-writing`; для утверждённого текста не подключать.
5. При выборе структуры новой спеки, перестройке каталогов или архитектуры local components прочитать [разбор итоговой спеки Постпэя](references/postpay-reference-pattern.md). Он фиксирует проверенные пользовательские исправления; продуктовые значения и размеры примера не являются универсальной нормой.

Не загружать все modules механически для узкого read-only запроса. Полная новая или смешанная задача обычно требует их все.

## Входной контракт

До записи определить:

- продукт, platform, role;
- утверждённые source frames и точный target node;
- начало/конец изменения и разрешённый объём;
- source of truth для поведения;
- обязательные сценарии и states;
- `out of scope`, gaps и вопросы.

Для внутреннего проекта проверить доступные Wiki, Tracker и релевантный продукт/prototype. Недоступное обозначить как gap. Если неизвестный ответ меняет логику, конечный экран, сохранение, права или состав состояний — спросить и приостановить только зависящие от ответа изменения. Продолжать подтверждённую независимую часть. Размеры, variants, bindings и geometry выяснять в Figma.

## Исполнение

1. Классифицировать задачу: spec-only, mockup-only или смешанная.
2. Провести read-only audit target, пользовательских исправлений, hierarchy, components, variables, styles, modes и geometry в объёме задачи. Найти аналоги внутри согласованного target.
   Перед серией записей зафиксировать mutation allowlist и protected invariants по workflow; изменение вне allowlist останавливает тиражирование.
3. До раскладки выбрать главную продуктовую ось и составить карту линейных сценариев и независимых состояний. Аналогичные варианты показывать в одинаковом порядке; не ограничивать ряд тремя экранами. Для точечной правки достаточно затронутых связей или состояний.
4. Проверить product organism → Base component → composition → local component; свободные слои использовать последними.
5. В существующей `[SPEC]` работать in place. Не заменять её целиком и не удалять пользовательские nodes без прямого запроса.
6. Сначала довести один репрезентативный row, затем перенести проверенный pattern на все аналоги. Если пользователь потребовал сначала показать эталон, дождаться его явного подтверждения; изменение дельты или области требует нового подтверждения.
7. Стрелки ставить после финального layout: `source root frame → actual trigger/hit area → next root frame`; для системного события или подписанной серии действий использовать frame-anchor по arrow-reference. После move/resize/gap проверять endpoints заново.
8. Для полного build или handoff пройти `quality-gates.md`; для изолированной правки выполнить numeric/visual check из выбранного профильного reference.

## Неподвижные правила

- Не создавать `Draft spec` без прямого запроса.
- Строка линейного сценария — один путь; строка каталога — одна тема с сопоставимыми состояниями. Число кадров не фиксировано.
- Независимые состояния не соединять стрелками.
- Не начинать row с необъяснённого промежуточного экрана.
- Для явного действия через контрол tail касается полного hit area, arrowhead — следующего root frame; для системного события или подписанной серии действий использовать frame-anchor по arrow-reference. Проверять реальные концы линии, не bounds instance.
- Overlay показывает полный релевантный контекст под ним; значимый content и actions не обрезаются.
- Не считать визуально совпавший цвет, шрифт или spacing токеном без binding/style.
- Не создавать local master, если доступен правильный library component.
- Исправление instance или экрана не разрешает менять общий master с другими потребителями; для такой записи сначала показать радиус воздействия и получить отдельное согласие.
- Local components моделируют переиспользуемые смысловые блоки и их конфигурацию. Ошибка, scroll offset или шаг сценария сами по себе не являются причиной создавать новый variant целой шторы.
- Внешний фон секции спеки — `#000000`. Product UI следует ДС; оболочка, подписи и связи следуют принятому оформлению спеки и могут использовать ручные значения.
- Пользовательский исправленный пример переносить на аналоги в согласованной области; для другого продукта или платформы проверить применимость.
- Если пользователь не видит выполненную правку, не повторять write автоматически: перечитать стабильный node ID, проверить файл/страницу/узел и получить свежий screenshot.
- Передавать ссылку на существующий итоговый node, покрытие и оставшиеся gaps со статусом проверки. Не называть результат полностью проверенным без numeric и visual QA.
