# HTML-прототип → Figma-спека

Восстановить принятое решение из работающего прототипа, собрать редактируемые экраны из связанных компонентов Figma и передать их в `figma-spec-builder`. Начинать с кода и карты соответствий, затем проверять конкретные библиотечные источники и результат на экране.

## Границы и вход

По умолчанию перенос сохраняет согласованные тексты, логику и вид. Он разрешает необходимую реконструкцию экранов, но не продуктовый редизайн. Если нужны только макеты, закончить после их проверки; если просят спеку, довести всю цепочку без дополнительного согласования уже запрошенных этапов. Для исходника, который уже находится в Figma, использовать `figma-spec-builder` напрямую. Обратное направление Figma → HTML принадлежит `figma-to-baseai`.

Выяснить из запроса, файлов и контекста:

- HTML-файл и корень его проекта с CSS/JS/assets либо URL прототипа;
- нужную версию, платформу, роль, viewport и границы переносимого сценария;
- точный целевой Figma-файл и узел, существующую спеку, если она есть;
- что подтверждает целевое поведение: решение пользователя, требования, исходник и его исправления.

Не спрашивать размеры и component properties, доступные в источниках. Если неизвестен target, сначала продолжить локальный разбор; запись ждёт точного назначения. Если неизвестное меняет сохранение, права, ошибку или конечный результат, уточнить только это поведение и продолжить независимую часть. Исправленный пользователем итоговый макет имеет приоритет над старым прототипом в затронутой области.

Для Travel выполнять правила контекста из workspace `AGENTS.md`. Внутренние продуктовые знания остаются в паспорте и артефактах задачи; не копировать их в этот скилл или общую карту компонентов.

## 1. Разобрать исходник

Прочитать [разбор исходника и состояний](references/source-and-state-contract.md). Для локального HTML запустить поставляемый инспектор, подставив реальные пути:

```sh
python3 "<skill-dir>/scripts/inspect_html.py" \
  --html "<project-root>/prototype/index.html" \
  --workspace "<project-root>" \
  --output "<task-artifacts>/html-inventory.json"
```

При `--output` каталог отчёта создаётся по указанному пути; без этого флага JSON выводится в stdout. По умолчанию используется [общая карта](references/component-map.json); `--map` заменяет её картой проекта. Если проверено, что сервер раздаёт `/BaseAI/` или `/Base2.0/` от корня проекта, добавить `--web-root "<project-root>"`: без явного document root скрипт оставляет root-relative URLs неразрешёнными. Скрипт только читает исходники, не исполняет JavaScript и не обращается к сети. Его JSON — статические наблюдения и кандидаты, а не доказательство runtime-поведения или связи с библиотекой Figma.

Прочитать релевантные зависимости, дополнительные стили и обработчики; затем открыть прототип доступным браузерным инструментом. При HTML-оболочке с рендерингом из JS разбирать фактический DOM и исходные компоненты приложения: пустой статический inventory не означает отсутствие интерфейса. URL анализировать через доступный браузер и разрешённый доступ к коду; не выдавать screenshot-only разбор за инвентаризацию компонентов.

## 2. Разрешить компоненты

Прочитать [контракт карты](references/component-mapping.md). Подключить доступный `travel-figma-design-system` и его карты по маршрутизации. Общий JSON хранит кандидатов и ссылки на доказательства; загружать только нужные записи и релевантную часть внешних индексов.

До первой записи полностью прочитать `travel-figma-design-system/references/readiness-gate.md` и запустить его `scripts/preflight.mjs`. Этот preflight подтверждает только локальное знание Base 2.0/Organisms; затем read-only вызовами проверить доступность живых libraries, нужных masters, variables/styles и modes в целевом Figma-файле. Наличие скилла, JSON-индекса или похожего имени компонента не означает, что библиотека подключена.

Для каждого самостоятельного блока и вложенного контрола:

1. Сопоставить код с общей или проектной картой: библиотека кода, selector/classes, modifiers, вариант, слоты и overrides. Имя класса само по себе не доказывает соответствие.
2. Проверить имеющийся Code Connect. Затем проверить связанные instances существующих экранов. Только для неразрешённых элементов искать в живой библиотеке средствами `figma:figma-generate-design`.
3. Выбрать наиболее специфичный целый product organism; далее Base component → композиция связанных компонентов → обоснованный local component. Не заменять целый опубликованный drawer или modal своим wrapper из его внутренних частей.
4. В Figma проверить key и его тип, актуальный master, platform/role, публикацию, variant axes, реальные properties и slots. `componentSetKey` не использовать как ключ одиночного component. Даже запись `verified` — датированное соответствие; перед импортом проверить текущую доступность и применимость.
5. Разрешить CSS-токены в семантические Figma variables/styles и нужный mode. Цвет HEX, одинаковый шрифт или число отступа без binding не считаются токеном. Иконки проверять по источнику, семантике, поколению, точному размеру slot и цвету в host.

Для текущей задачи вести карту `элемент исходника → выбранный master/key → properties/slots/tokens → evidence → статус`. Если совпали несколько записей, не выбирать первую автоматически. Недоступную библиотеку, неизвестный variant или локальные CSS-переопределения обозначить как gap. При конфликте принятого вида с системным компонентом найти поддерживаемую конфигурацию; не менять утверждённый UI молча ради совпадения с библиотекой.

До записи посчитать:

- `Component coverage`: значимые блоки всего / разрешены в linked library instance / согласованы как local / unresolved.
- `Token coverage`: semantic variables/styles / подтверждённые исключения / unresolved literals.

Крупные блоки и интерактивные controls с unresolved master, variant, slot или source library блокируют зависимую часть переноса. Semantic color, typography, radius или effect без реального binding также остаётся blocker; совпавшее значение не закрывает проверку. Не заменять их визуальной копией из свободных layers.

## 3. Зафиксировать состояния и восстановить экраны

Составить компактную карту сценариев: точка входа → действие → изменение → результат; отдельно — независимые состояния. Для каждого правила сохранить источник и статус по reference. Существующий обработчик, атрибут `disabled` или имя `error` не подтверждают backend-контракт. Не превращать дефект прототипа в требование и не дорисовывать неизвестный результат ради полноты.

До записи прочитать доступные `figma:figma-use` и `figma:figma-generate-design`; проверить фактически доступные чтение дерева, запись, разрешение library masters, variables/styles и визуальный просмотр. Наличие скиллов не означает доступность этих инструментов. Если доступа нет, завершить доступный разбор и явно назвать, что осталось до переноса; локальный отчёт не является Figma-спекой.

Собирать экраны по `figma:figma-generate-design`: сначала один репрезентативный экран со сложным блоком, затем перечитать его дерево и проверить `INSTANCE → mainComponent/key → properties/slots`, variable/style bindings и screenshot. Только после PASS тиражировать остальные. Если пользователь потребовал подтвердить эталон, остальные экраны не записывать до его явного согласия; изменение дельты или области требует нового подтверждения.

Перед серией записей определить mutation allowlist и protected invariants для целевых nodes, geometry, component linkage, bindings и пользовательских правок. После эталона проверить read-back; изменение вне allowlist останавливает тиражирование. Разрешение перенести экран не разрешает менять общий master: проверить потребителей и получить отдельное согласие. Если пользователь не видит результат, сначала перечитать стабильный node ID, проверить файл/страницу/узел и получить свежий screenshot, не повторяя write вслепую.

Сохранять авторазметку, реальные slots и связанные instances; повторяемую смысловую композицию моделировать один раз. Захват веб-страницы использовать по правилам Figma-интеграции для сверки геометрии и переноса изображений; он сам по себе не подтверждает компонентную структуру.

`figma-design-machine` подключать, если пользователь просит также продуктовые изменения или недостающие макеты в пределах подтверждённого поведения. Сам перенос принятого HTML не требует нового поиска концепций. Не останавливать цепочку для повторного разрешения на уже согласованную реконструкцию.

## 4. Собрать спеку и передать результат

Когда нужны спеки, передать `figma-spec-builder` проверенные source frames, точный target, карту сценариев/состояний, компонентные соответствия и нерешённые gaps. Прочитать его обязательное ядро и профильные references; оболочку, стрелки, каталоги и quality gates выполнять там, не поддерживать здесь вторую копию этих правил. Существующую `[SPEC]` дорабатывать на месте в согласованной области.

После последних изменений проверить:

- вид и поведение переносимых состояний при согласованном viewport, включая scroll, sticky и overlays;
- реальные связи `screen → local composition → library components`, свойства, токены, modes и изображения;
- соответствие сценариев подтверждённому источнику и границы неизвестного;
- numeric и visual QA макетов и, если запрошена, итоговой спеки.
- финальные числа component/token coverage и отдельные статусы локальных snapshots, живых Figma libraries и Storybook/BaseAI provenance исходника.

Для двух и более названных результатов — например, макетов, тем, спеки и общего master — отдельно фиксировать статус записи и проверки каждого; не объявлять общее завершение при частичной готовности.

В ответе дать ссылки на фактические итоговые nodes, покрытие сценариев и состояний, числа component/token coverage, какие компоненты связаны с библиотекой и какие остаются локальными или неразрешёнными. Отдельно назвать статусы live Figma libraries, Storybook/BaseAI provenance и невыполненные проверки. Полноту переноса не выводить из успешного запуска инспектора.
