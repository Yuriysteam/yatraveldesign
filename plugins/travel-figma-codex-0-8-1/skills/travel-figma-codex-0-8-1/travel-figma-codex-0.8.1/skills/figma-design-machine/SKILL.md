# Figma Design Machine

Превращать продуктовую задачу в проверяемый набор согласуемых экранов внутри существующего Figma-файла. Работать как продуктовый дизайнер: сначала определить решение и состояния, затем собирать интерфейс из дизайн-системы.

## Обязательные входы

Получить или вывести из контекста:

- точную ссылку на Figma-узел с `fileKey` и `nodeId`;
- платформу и размер baseframe;
- роль пользователя, сценарий и основное действие;
- доступные материалы: макеты, код, документация, исследования;
- режим: `repair`, `one-solution`, `concepts` или `mixed`;
- точную границу допустимых изменений и `out of scope`.

Не задавать повторно вопросы, на которые пользователь уже ответил. Если неизвестное решение заметно меняет продуктовый сценарий, спросить; в остальных случаях сделать и явно пометить рабочую гипотезу.

## Рабочий процесс

1. Загрузить навыки `figma:figma-generate-design` и `figma:figma-use` до операций записи.
2. Полностью прочитать соседний [Travel Figma Design System](../travel-figma-design-system/SKILL.md) и маршрутизировать его карты по типу задачи до выбора или изменения product components.
3. Разобрать точный baseframe: размер, иерархию, компоненты, шрифты, переменные, стили и доступное место на канвасе.
4. Проверить Code Connect в коде, если код дан. Затем проверить компоненты существующего экрана. Только для неразрешённых элементов искать библиотеку через `get_libraries` и `search_design_system`.
5. Сформулировать продуктовую задачу: пользователь, контекст, работа, решение, основное действие, критерий успеха и риски.
6. Составить контракт контента для каждой повторяемой сущности: обязательные поля, действия, состояния и ограничения длины.
   Контентное изменение определить как продуктовое правило, редакционное правило или демонстрационные данные; неоднозначную массовую правку сначала проверить на одном примере.
7. В режиме `concepts` сделать столько направлений, сколько требует задача. Если число не задано, выбрать минимальный набор действительно разных приоритетов; не выдавать косметические варианты за концепции. Для каждого зафиксировать выигрыш, потерю и подходящий сегмент.
8. До сборки составить state matrix из реальных рисков сценария: причина состояния → что сохраняется → что меняется → доступное восстановление. Не добавлять состояния только ради каталога.
9. Собрать wrappers из переданного baseframe. Сохранять системные шапки, навигацию и контейнеры дизайн-системы.
10. Повторяемый контент оформлять компонентом или слотом один раз и размещать экземпляры. Не дублировать плоские карточки.
11. Зафиксировать решение и правила состояний, необходимые для согласования макетов. Если пользователь просит рабочую Figma-спеку, после принятия решения применить отдельный `figma-spec-builder`, не дублируя его workflow внутри этого навыка.
12. Проверить каждый экран скриншотом. Исправить обрезку, ранние переносы, пересечения, неправильные variants, неверные bindings и остаточные временные placeholders.
13. Вернуть ссылки на каждый Figma-узел, покрытие states, исключения и коротко назвать рекомендуемую концепцию.

## Безопасная запись

- Если пользователь просит сначала показать один эталон, менять только его до явного подтверждения. Изменение дельты или области аннулирует подтверждение; после пакетной регрессии вернуться к эталону.
- Перед серией правок определить mutation allowlist и protected invariants: разрешённые узлы/свойства и то, что обязано сохраниться. После эталона сравнить read-back; посторонняя дельта останавливает распространение.
- Разрешение исправить экран или instance не разрешает менять общий master. Сначала проверить потребителей, сообщить радиус воздействия и получить отдельное согласие; локальная настройка не должна приводить к detach или нарушению DS.
- Если пользователь не видит результат, не повторять write автоматически. Перечитать стабильный node ID, проверить файл/страницу/узел и получить свежий screenshot; повтор разрешён только при доказанном отсутствии изменения.
- Для двух и более явно названных артефактов, тем или типов целей вести отдельные статусы записи и QA; не сворачивать частичную готовность в «готово».

## Продуктовые правила

Правила сохранения данных, восстановления и обработки ошибок ниже — UX-рекомендации для нового решения. В доработке утверждённого продукта сначала сверить фактический контракт; в спеке не выдавать рекомендации за подтверждённое backend-поведение. Неизвестное, влияющее на результат, уточнить; независимую подтверждённую работу продолжать.

- Не придумывать подтверждённые продуктовые факты и реальные расписания. Демонстрационные данные обозначать как пример.
- По умолчанию оптимизировать не плотность макета, а решение пользовательской задачи.
- Сохранять готовые данные при частичной ошибке.
- Loading должен сохранять геометрию результата.
- Ошибка изображения не должна блокировать карточку и основное действие.
- Фильтры и параметры поиска сохранять после ошибки загрузки.
- Наследовать точные размеры и responsive-поведение переданного baseframe. Размеры из исторических product packs не превращать в универсальные правила.
- Использовать продуктовые шрифты из baseframe; не подменять их Inter.

## Формат концепций

Для каждого направления записать:

- `Приоритет`: что пользователь считывает первым;
- `Подходит`: для какого контекста или сегмента;
- `Цена решения`: что становится менее заметным или требует раскрытия;
- `Рекомендация`: основной вариант для первого запуска и причина.

## Definition of Done

- Все экраны имеют правильный размер и расположены без пересечений.
- Использованы связанные компоненты, переменные и стили дизайн-системы, где они доступны.
- Повторяемые карточки компонентизированы.
- Представлены только релевантные normal/loading/empty/no-results/error/partial/media/permission/limit states, выведенные из state matrix.
- Нет остаточных временных placeholders, обрезанного текста и неизвестных шрифтов. Loading-skeleton используется как спроектированное состояние загрузки. Постоянный медиаплейсхолдер при отсутствии фото допустим по продуктовому правилу, в том числе с цветовым Skeleton token; сам token не означает загрузку всего экрана. Не заменять доступные фото плейсхолдерами при DS-repair.
- Для согласования зафиксированы неочевидные правила поведения и различия состояний.
- Пользователь получил прямые ссылки на созданные узлы.
- Границы изменения, рабочие гипотезы, DS-исключения и нерешённые gaps названы явно.

## Контекст проекта

При работе именно в файле B2B Travel Builder прочитать [references/b2b-travel-builder.md](references/b2b-travel-builder.md). Для любого другого файла считать её историческим product pack: не переносить размеры, node IDs, железнодорожные фильтры и принятые решения без повторной проверки контекста.
