# Travel UI Delivery

Один видимый конвейер для небольших UI-задач. Дизайнер задаёт намерение и визуальный источник; агенты находят код, реализуют платформенные изменения, доказывают результат снимками и передают PR разработчику.

## Quick Reference

- `analyze`: только карта влияния.
- `draft`: карта → реализация → снимки → дизайн-ревью, без PR.
- `deliver`: то же самое + отдельный `review-only` PR на платформу после показа точного плана публикации и согласия пользователя на него.
- `analyze` принимает тикет или Figma; `draft` требует точный Figma-узел; `deliver` требует тикет и точный Figma-узел.
- Большая или продуктово неоднозначная задача возвращается дизайнеру как `out_of_scope`.

## Роли

Координационные роли определены в [`../../agents/`](../../agents/):

- `travel-ui-impact-mapper` — read-only карта влияния;
- `travel-ui-visual-reviewer` — независимая проверка снимков против Figma;
- `travel-ui-delivery-orchestrator` — единственная роль, которая принимает решения и управляет PR.

Продуктовый код напрямую пишут штатные агенты Travel `ios-coder`, `coder`, `worker-bee` по [единому контракту](references/run-contract.md); промежуточных платформенных адаптеров нет.

## Порядок работы

1. Определи режим по запросу. Анализ не даёт разрешения на изменения; просьба «сделай PR» выбирает `deliver`.
2. Проверь доступность и совместимость контрактов `travel-ui-impact-map`, `travel-ui-visual-evidence` и `arc-pr-delivery`; несовместимость верни как `tooling_gap`. Затем запусти карту влияния.
3. До любых правок проведи для каждой затронутой платформы [платформенный шлюз](references/platform-code-rules.md). Он обязан установить источники архитектурных правил, владельца состояния и окружения, план переиспользования, перекрёстную матрицу сценариев и работоспособный путь сборки/снимков. Пока карта и шлюз платформы не имеют статус `ready`, не запускай её исполнителя.
4. Покажи дизайнеру короткую карту: платформы, состояния и контексты, предполагаемые файлы, прочитанные правила, переиспользуемые компоненты и открытые вопросы. Спрашивай только о решениях, которые нельзя вывести из источников.
5. Для каждой платформы создай отдельный безопасно занятый checkout/ветку и напрямую передай штатному агенту проекта (`ios-coder`, `coder` или `worker-bee`) пакет по [единому контракту запуска](references/run-contract.md): буквальные `allowed_paths`, результат шлюза, Figma-контекст, состояния и проверки. Если агент недоступен и в актуальной ревизии не найден его преемник, верни `tooling_gap`. Параллельны только платформы в разных checkout.
6. Штатный агент до правок сверяет шлюз с актуальным checkout, реализует минимальную дельту, запускает штатные тесты/снимки и проверяет diff. Если контракт расходится с кодом, правила не найдены, путь проверки не работает или нужен файл вне `allowed_paths`, агент возвращает `blocked` или `scope_change_required` с доказательствами. Оркестратор повторно проводит шлюз перед продолжением. Новая абстракция допустима только при подтверждённом повторном использовании.
7. После закрытия всех пишущих агентов запусти `travel-ui-visual-evidence` через независимого проверяющего. Исполнитель не утверждает сам, что его результат совпал с макетом.
8. При `needs_fix` верни замечания штатному агенту соответствующей платформы и повтори снимки/ревью. После двух повторений одного и того же blocker остановись и запроси недостающее решение; новый конкретный технический сбой обрабатывай в рамках платформенных ограничений.
9. В режиме `deliver` подготовь один PR на платформу по [контракту выпуска](references/run-contract.md) и шаблону [описания PR](references/pr-template.md). Покажи план `arc-pr-delivery`, получи точное согласие на режим и список файлов, затем используй `review-only`; не делай self-Ship и auto-merge.
10. После создания прочитай каждый PR: точный набор файлов, активный diff, проверки, публикация и назначенные ревьюеры. Если разработчик не назначен, оставь PR открытым и явно сообщи пробел.

## Ворота малой задачи

Задача подходит конвейеру, если у неё один локальный пользовательский эффект, ограниченный набор состояний и нет миграции данных/архитектуры. Верни `out_of_scope`, когда требуется продуктовый выбор, крупная навигационная перестройка, несколько зависимых сервисов или неизвестный контракт backend.

PR запрещён, если:

- Figma указывает на страницу/холст вместо точного состояния;
- статус карты конкретной платформы не `ready`;
- платформенный шлюз не `ready`: не зафиксированы актуальные правила, источник значимого состояния/окружения, перекрёстные сценарии или штатные команды проверки;
- хотя бы одно `required` или `regression` состояние не воспроизводится снимком;
- визуальная проверка не `ready_for_pr`;
- план `arc-pr-delivery`, режим и точные пути не показаны пользователю и не подтверждены им перед мутацией.

## Итоговый вывод

Верни статус, ссылки на источники, по каждой платформе — файлы, снимки, результат дизайн-ревью и PR. Отдельно перечисли решения дизайнера и оставшиеся риски. Не называй задачу завершённой только по факту создания PR.
